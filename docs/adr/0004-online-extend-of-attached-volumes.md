# Extend attached volumes: the driver grows raw files, Nova grows qcow2 files

Cinder can extend an attached (in-use) volume: the driver grows the backing storage, then Cinder sends Nova a `volume-extended` event and Nova's libvirt driver calls `virDomainBlockResize` so the guest sees the new size. Nova's NFS volume driver has supported this since Victoria. Upstream's generic `NfsDriver.extend_volume` still refuses attached volumes (bug 1870367) because `qemu-img resize` cannot run on a file a running qemu holds, and its snapshots are qcow2 overlay chains. Neither applies to us: VMstore snapshots are not files, so the active file is always `volume-<id>` (VMTS-243).

We report `online_extend_support: True` and, for attached volumes, choose by file format:

- **raw:** the driver grows the file with `truncate` and verifies its size. Growing a raw file only changes its length, which is safe while a VM writes to it; Nova then makes the guest see it.
- **qcow2:** the driver **never modifies the file while a VM may hold it**. The virtual size lives in the image header and the allocation tables, which a running qemu caches in memory. VMstore shares are mounted `nolock` (`local_lock=all`), so qemu's lock on a compute host is invisible from the Cinder host and `qemu-img resize` does not refuse. Nova/qemu resizes the image instead.
- **qcow2 on shut-off instances:** Nova skips the guest-side resize when the instance is not running, so nothing would grow the file. If Nova (via the `[nova]` credentials) reports every attached instance as `SHUTOFF` with no task in progress and `power_state` SHUTDOWN (4), the driver resizes the file with `qemu-img resize`. `status` comes from `vm_state` in the Nova database while `power_state` follows the hypervisor, so both must agree; CRASHED is refused because qemu may still hold the file. An attachment whose server Nova does not know (an orphan left by a deleted server) is skipped; if no attached server exists, nothing is confirmed. Any other doubt (Nova error, a missing `OS-EXT-STS` attribute, a host attachment with no instance, `vmstore_online_extend_nova_check = False`) leaves the file alone.
- **Re-check after the offline resize:** if Nova then reports an instance as no longer shut off, the extend fails with `ExtendVolumeError` (the file is already resized and must be checked with `qemu-img check`); if Nova cannot answer, the driver logs a warning and the extend succeeds.
- **Format:** `qemu-img info` probes data the guest can write. A guest can put a qcow2 header in a raw volume, but cannot make a qcow2 file look raw, so the file is handled as raw if the probe, the recorded `admin_metadata['format']` or the format Nova opened it with (the attachment's `connection_info`) says raw. A recorded `qcow2` is not trusted: `_do_create_volume` records `qcow2` before `copy_image_to_volume` converts a volume created from an image to raw. Since VMTS-252, `copy_image_to_volume` records `raw`, but volumes created earlier keep the stale record. The same rule decides the format `initialize_connection` reports to Nova and the one reconcile-on-attach grows the file as, so the driver never resizes a planted header as qcow2 on a volume recorded as raw. Whether Nova then opens the file with the reported format depends on the Nova build: some builds probe the file themselves and ignore it (observed in the lab on 2026-10-19), so a guest-written header can still change how the volume is opened after the next attach; that is outside the driver. A qcow2 header with an external data file or an unexpected backing file is already refused by Cinder's `qemu_img_info` (format inspector) and `_qemu_img_info`.
- **Never shrink:** a file already larger than the new size (left by an extend whose size check failed, or grown outside Cinder) is refused, and one already at the new size is left as is, so a retried extend succeeds. raw sizes are read from the file length, not the probe.
- **Safety net:** `initialize_connection` grows a file whose virtual size is smaller than the volume size, under the volume lock, but only when no other attachment is in the `attached` state. This repairs a resize Nova skipped or failed before the next consumer opens the file. It runs on a new attach only (attach, unshelve, cold migration): starting or rebooting an instance does not call `initialize_connection`, and a live migration keeps the source attachment attached.

Everything is validated (larger size, share space, format) before the file is touched, so a failed extend leaves the volume at its original size, except for the re-check failure above. Cinder still marks it `error_extending`; that status comes from Cinder core, which also records a `DRIVER_FAILED_EXTEND` user message.

## Evidence

Validated on the Platform9 staging lab (2026-10-10) with continuous write-and-verify I/O: raw grow under I/O plus `blockResize`, qcow2 `blockResize` alone, and offline grows of both all passed with 0 bad blocks out of 363,819. An external `qemu-img resize` of a qcow2 image held by a running VM on another host made qemu mark the image corrupt (`Preventing invalid write on metadata (overlaps with active L1 table)`) on its next metadata write.

## Consequences

- An attached qcow2 extend reported successful by Cinder depends on Nova applying it; Cinder gets no feedback (upstream's `os-extend_volume_completion` flow is not used by Nova). If Nova does not apply it, the guest keeps the old size until the next attach.
- Both the VMstore and our provisioned-capacity scan (ADR-0001) count file length, so an online-extended qcow2 volume is under-counted until data is written.
- The driver now calls the Nova API for attached qcow2 extends; deployments without `[nova]` credentials fall back to the Nova-only path.
- If a qcow2 instance is shut off and the Nova check is disabled or fails, Nova skips the resize and the guest keeps the old size until the volume is attached again; a power-on or reboot does not apply it. The driver logs a warning in that case.
- For a running instance, Cinder reports the extend successful once the volume-extended event is sent; a later `blockResize` failure in Nova is only visible in Nova (instance actions and logs).
- The offline qcow2 resize leaves a window of about the length of `qemu-img resize` in which a power-on requested after the Nova check could open the file. The re-check catches it after the fact; it does not prevent it.
- The Nova calls run under the volume coordination lock, up to `vmstore_nova_api_timeout` seconds each. That is one call while the driver reports `multiattach: False`; revisit if multiattach is enabled.
- Detached volumes no longer use the parent `NfsDriver.extend_volume`, which passed the stale `admin_metadata['format']` to `qemu-img resize`, so extending a detached volume created from an image failed with `Image is not in qcow2 format` (VMTS-252, reproduced in the lab on 2026-10-19). They go through the same format rule and `_grow_volume_file` (never shrink, verify), under the volume lock; no VM holds the file, so qcow2 is resized directly.
